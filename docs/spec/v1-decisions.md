# Lookout v1: decisions and evidence

The v1 specification is [issue #1](https://github.com/chasepie/lookout/issues/1). Its [prototype follow-up comment](https://github.com/chasepie/lookout/issues/1#issuecomment-6257522502) recorded what the [#2 prototype](../research/browser-and-vpn-prototype.md) changed and asked three open questions. This checklist accounts for every statement and question in that comment, and for the parts of the issue body that the implementation deliberately settled differently, linking each to its decision and evidence. Reconciled in [#41](https://github.com/chasepie/lookout/issues/41).

A ticked item is decided and implemented, with the evidence linked. An unticked item is waiting on the open ticket named.

Tests are linked by file and named by test. `Backend` tests are in [`tests/Backend.IntegrationTests`](../../tests/Backend.IntegrationTests), and runner tests are in [`src/runner`](../../src/runner).

## Deployment validation

- [x] **Smoke test of the real VPN stack**: [#42](https://github.com/chasepie/lookout/issues/42), run on 2026-10-26 and recorded in [the VPN smoke test report](../research/vpn-smoke-test.md). Every VPN check passed live against gluetun and PIA: exits, scheduled and early Rotation with its 3-minute minimum, draining, refused Test runs, failing closed and recovery, WebRTC, headful Chromium, the control-server role, the bounded OpenVPN attempts and the server-list refresh, as did runner isolation. The one failure, pages Browserless loads reaching Lookout through the Docker host's published port, is accepted below (#44). Items below that rest only on deployment configuration name #42 as their validation.
- [x] **Pages Browserless loads can reach Lookout through the Docker host**: [#44](https://github.com/chasepie/lookout/issues/44), found by #42. Decided: document it, don't restrict it. Such a page reaches Lookout's published port like any LAN device, and Lookout's login, request-token header and `SameSite=Strict` cookies still apply, so it gets only what needs no login. A Direct Run's browser reaches the LAN anyway. The residual risks are password guessing without rate limiting (ADR-0002) and setting up the account on a fresh install before its owner does ([ADR-0006](../adr/0006-browser-pages-reach-lookout-like-a-lan-device.md)). Evidence: the report's browser-to-backend table; README "Smoke test" step 10 and VPN step 7 now check it.

## Prototype follow-up comment

Evidence: [`browser.spec.ts`](../../src/runner/browser.spec.ts): `a connecting runner asks for a headful Chromium with the flags that hide automation and the home IP`.
- [x] **`--disable-blink-features=AutomationControlled` and `--webrtc-ip-handling-policy=disable_non_proxied_udp` on every Browserless connection**, including Direct Runs and Test runs: kept ([ADR-0004](../adr/0004-gluetun-for-vpn-rotation.md), [runner README](../../src/runner/README.md)). - [x] **Browserless's `TIMEOUT` above the 10-minute maximum Watch timeout**: `TIMEOUT: 660000` (11 minutes) in [`compose.yaml`](../../compose.yaml), from [#28](https://github.com/chasepie/lookout/pull/28). Evidence: the README's manual smoke test, step 7.

### VPN

- [x] **A Rotation is one or more attempts, each `stopped` then `running`**, complete only on an exit IP different from the one noted before its first attempt, which is kept for the whole Rotation ([ADR-0004](../adr/0004-gluetun-for-vpn-rotation.md), [#34](https://github.com/chasepie/lookout/pull/34)). Evidence: [`VpnRotationTests`](../../tests/Backend.IntegrationTests/VpnRotationTests.cs): `ARotationMakesAnotherAttemptUntilTheExitIpChanges`; [`GluetunVpnRotatorTests`](../../tests/Backend.IntegrationTests/GluetunVpnRotatorTests.cs): `RotatesByStoppingThenStartingTheVpn`, `RetriesStartingTheVpnSoARotationDoesNotLeaveItStopped`.
- [x] **Connected requires an exit IP**: `GET /v1/vpn/status` saying `running` isn't enough. The exit IP is `GET /v1/publicip/ip`'s, or one fetched through the proxy (via the runner and Browserless) once gluetun has had none for 10 s, at most every 10 s ([ADR-0004](../adr/0004-gluetun-for-vpn-rotation.md)). Evidence: `GluetunVpnRotatorTests`: `SaysWhyTheVpnIsDisconnectedUnlessItIsRunningWithAPublicIp`, `CountsAnExitIpFetchedThroughTheProxyWhenGluetunHasHadNoneForTenSeconds`, `ChecksThroughTheProxyAtMostEveryTenSecondsUntilOneFindsAnExitIp`, `ARotationForgetsTheExitFoundThroughTheProxy`.
- [x] **Another attempt after about 15 s without a new IP**, with VPN Runs still paused, not counted against the early-Rotation limit ([ADR-0004](../adr/0004-gluetun-for-vpn-rotation.md)). Evidence: `VpnRotationTests`: `ARotationMakesAnotherAttemptUntilTheExitIpChanges`, `EarlyRotationsComeAtMostOnceEveryThreeMinutes`.
- [x] **Startup recovery**: with no noted IP, any exit IP means ready. If none arrives within about 15 s of gluetun's control server first answering, the rotator makes an attempt ([ADR-0004](../adr/0004-gluetun-for-vpn-rotation.md)). Evidence: `VpnRotationTests`: `RotatesWhenTheVpnHasNotConnectedFifteenSecondsAfterStartup`, `TimesTheCheckAtStartupFromWhenGluetunFirstAnswers`.
- [x] **Decision needed: refuse or wait?** Resolved: VPN Runs wait. A VPN Run whose VPN isn't connected waits up to 2 minutes, giving its Run slot to other Runs meanwhile and taking the next free one first, then is recorded as Errored without running its Script, with a message saying why. It never falls back to a Direct Run. With no VPN configured, or a key gluetun refuses, it's Errored at once. A VPN Run that comes due during a Rotation waits for it to end ([ADR-0004](../adr/0004-gluetun-for-vpn-rotation.md), [#33](https://github.com/chasepie/lookout/pull/33), [#34](https://github.com/chasepie/lookout/pull/34), [#35](https://github.com/chasepie/lookout/pull/35)). Evidence: [`VpnRunsTests`](../../tests/Backend.IntegrationTests/VpnRunsTests.cs): `AVpnRunWaitsForTheVpnToConnect`, `AVpnRunIsRefusedAsErroredWhenTheVpnDoesNotConnectWithinTwoMinutes`, `AVpnRunIsRefusedAsErroredAtOnceWithoutAVpn`, `AVpnRunIsRefusedAtOnceWhenTheVpnIsMisconfigured`; [`RunsTests`](../../tests/Backend.IntegrationTests/RunsTests.cs): `AVpnRunWaitingForTheVpnLendsItsSlotAndTakesTheNextOneFirst`; `VpnRotationTests`: `NoVpnRunStartsDuringARotationWhileDirectRunsCarryOn`.
- [x] **Control-server role**: `GET`/`PUT /v1/vpn/status`, `GET /v1/publicip/ip`, `GET`/`PUT /v1/updater/status`, and nothing else, in [`compose.yaml`](../../compose.yaml)'s `gluetun-auth` config ([ADR-0004](../adr/0004-gluetun-for-vpn-rotation.md)). Evidence: `GluetunVpnRotatorTests`: `IsMisconfiguredWhenGluetunRefusesTheApiKey`; the real role is validated in #42.
- [x] **Bounded OpenVPN attempts**: `OPENVPN_FLAGS: --connect-retry-max 1 --connect-timeout 10` in [`compose.yaml`](../../compose.yaml), so gluetun leaves a dead server by itself in about 35 s ([ADR-0004](../adr/0004-gluetun-for-vpn-rotation.md)). Evidence: the prototype's measurements; deployment configuration only, validated live in #42.
- [x] **`HTTPPROXY_STEALTH=on`**, in [`compose.yaml`](../../compose.yaml) ([ADR-0004](../adr/0004-gluetun-for-vpn-rotation.md)). Evidence: the prototype; validated live in #42.
- [x] **Server-list refresh**: through `PUT /v1/updater/status` the first time Lookout sees the VPN connected after it starts, skipped if Lookout did one within 360 h (persisted in its database), with Rotations held off until it completes; then gluetun's own `UPDATER_PERIOD: 360h` into the persistent `gluetun-data` volume ([ADR-0004](../adr/0004-gluetun-for-vpn-rotation.md)). Evidence: `VpnRotationTests`: `RefreshesTheServerListWhenTheVpnFirstConnectsAtMostOnceEvery360Hours`, `ARefreshThatFailsIsTriedAgainAtTheNextStart`, `ARotationWaitsForTheServerListRefreshInProgress`; `GluetunVpnRotatorTests`: `RefreshesTheServerListThroughGluetunsUpdaterAndWaitsForItToComplete`.
- [x] **US-only `SERVER_REGIONS`**: refined to US defaults (eight US regions in `LOOKOUT_VPN_REGIONS`), with the regions left to the user and an advisory to keep them in one country, as another country's exit changes what retailers serve ([ADR-0004](../adr/0004-gluetun-for-vpn-rotation.md), README's VPN section).
- [x] **Setup docs cover the gluetun configuration** (story 63): README's VPN section.
- [x] **OpenVPN over TCP and UDP both worked**: recorded. Lookout uses TCP (`OPENVPN_PROTOCOL: tcp`); nothing depends on the choice.

### Open questions

- [x] **1. Retry limit and alerting.** Resolved: the noted exit IP is kept across attempts; an attempt is retried after about 15 s without a new IP; the Rotation gives up after 2 minutes without one, and VPN Runs start again. They still fail closed: if the VPN reconnected to the old exit, they go out through it until the next Rotation; otherwise each waits up to 2 minutes and is Errored. Settings shows the VPN as not connected, with gluetun's reason, pushed within 30 s. There is no install-wide VPN outage notification: each VPN Watch notifies through its own failure streak, on its first Errored Run ([ADR-0004](../adr/0004-gluetun-for-vpn-rotation.md), [#34](https://github.com/chasepie/lookout/pull/34)). Evidence: `VpnRotationTests`: `ARotationGivesUpWhenTheVpnDoesNotReconnect`, `PushesChangesInTheVpnStatusBetweenRotationsWithinThirtySeconds`; `VpnRunsTests`: `AVpnRunIsRefusedAsErroredWhenTheVpnDoesNotConnectWithinTwoMinutes`; [`NotificationsTests`](../../tests/Backend.IntegrationTests/NotificationsTests.cs): `AStreakOfErroredRunsSendsOneNotificationOnItsFirstRun`, `AScheduledRunNotifiesToo`. Live outage behaviour is validated in #42.
- [x] **2. How "changed" is changed?** Resolved: accept the risk. Any exit IP different from the noted one completes a Rotation, even in the same /24, ASN or region; v1 doesn't guarantee a different subnet or ASN, even for an early Rotation. A site that blocks by subnet or ASN may keep blocking until a Rotation happens to leave it ([ADR-0004](../adr/0004-gluetun-for-vpn-rotation.md), GLOSSARY's Rotation, README's VPN section).
- [x] **3. Test runs during a Rotation.** Resolved: both. A Rotation drains VPN Test runs in progress as it drains VPN Runs, and a VPN Test run requested during a Rotation is refused at once as Errored, saying to try again in a minute ([ADR-0004](../adr/0004-gluetun-for-vpn-rotation.md), [#34](https://github.com/chasepie/lookout/pull/34)). Evidence: `VpnRotationTests`: `AVpnTestRunIsRefusedAtOnceDuringARotationAndARotationWaitsForOne`; `VpnRunsTests`: `AVpnWatchsTestRunIsRefusedAtOnceUnlessTheVpnIsConnected`.

## Issue body: deliberate decisions

- [x] **Statuses**: a Watch with no Baseline is Pending unless a failure streak makes it Failing. Pausing keeps the Baseline and failure streak and clears the next Run; resuming schedules the next Run from now and keeps the failure streak, not a fresh one (story 15 superseded) ([GLOSSARY](../../GLOSSARY.md), [#27](https://github.com/chasepie/lookout/pull/27)). Evidence: [`WatchesTests`](../../tests/Backend.IntegrationTests/WatchesTests.cs): `ANewWatchIsPendingUntilItsFirstSucceededRun`, `AWatchWhoseFirstRunsFailIsFailingRatherThanPending`, `PausingKeepsTheBaselineAndResumingKeepsTheFailureStreak`.
- [x] **Notifications**: a failure streak sends one notification in total, on its first Errored Run or its third Known failure, whichever comes first. Recovered follows only a streak that notified, and only when a Baseline already exists; the Succeeded Run that sets a Baseline is silent. Recovering with different content sends Recovered, then Change ([#31](https://github.com/chasepie/lookout/pull/31)). Evidence: `NotificationsTests`: `AStreakOfErroredRunsSendsOneNotificationOnItsFirstRun`, `ThreeKnownFailuresInARowSendOneNotification`, `KnownFailuresBrokenUpByASucceededRunSendNone`, `RecoveringFromANotifiedFailureStreakSendsOneNotification`, `RecoveringWithDifferentContentSendsTheRecoveryThenTheChange`, `SettingTheBaselineSendsNone`, `SettingTheBaselineAfterANotifiedFailureStreakSendsNoRecovery`.
- [x] **Browser**: headful Browserless on Xvfb, superseding both the body's "headless" and the comment's user-agent rewrite ([ADR-0005](../adr/0005-headful-browserless.md)).
- [x] **Prototype questions 1–3 and their fallbacks**: answered by [#2](https://github.com/chasepie/lookout/issues/2) and [#21](https://github.com/chasepie/lookout/pull/21). Question 1's fallback (headful on Xvfb) was adopted; question 2's "refuse unless connected" became the wait-then-Errored admission above.
- [x] **Architecture**: five services rather than four: `lookout`, `runner`, `browserless`, and, in the `vpn` profile, `gluetun` and `gluetun-control`, a relay to gluetun's control server. Each pair of services that talk shares an internal network of its own (`runs`, `browsers`, `vpn-proxy`, `vpn-control`, `gluetun-control`); only `browserless` and `gluetun` reach the internet, `lookout` alone is on the LAN, and gluetun shares no network with Lookout ([README's Deploying section](../../README.md#deploying), [`compose.yaml`](../../compose.yaml), [#28](https://github.com/chasepie/lookout/pull/28), [#33](https://github.com/chasepie/lookout/pull/33), [#38](https://github.com/chasepie/lookout/pull/38)).
- [x] **Runner authentication**: the runner refuses requests without `RUNNER_TOKEN`, which only Lookout has, and Lookout won't start with a remote runner and no token ([#38](https://github.com/chasepie/lookout/pull/38)). Evidence: [`server.spec.ts`](../../src/runner/server.spec.ts): `given a token, a request is refused unless it carries that token, and executed when it does`; [`RunnerClientTests`](../../tests/Backend.IntegrationTests/RunnerClientTests.cs): `SendsTheConfiguredRunnerTokenWithEveryRequest`, `RefusesToStartWithoutARunnerTokenForARunnerOnAnotherMachine`.
- [x] **Published scripting package**: `@chasepie/lookout-scripting` on GitHub Packages, `edge` from `main` and `latest` from releases, alongside the images ([#39](https://github.com/chasepie/lookout/pull/39), README's Releasing section).
- [x] **Obsolete scaffolding**: the `Microsoft.Playwright` reference, `ScrapeController`, the runner's broken entry point and the named-export example were removed or replaced by [#19](https://github.com/chasepie/lookout/pull/19) and [#20](https://github.com/chasepie/lookout/pull/20); `docs/design/site-proposal.md` is deleted. None is outstanding v1 work.
- [x] **Time zone in Settings**: [#40](https://github.com/chasepie/lookout/issues/40). The install-wide time zone is a saved setting, chosen in Settings and shown beside daily and cron schedule inputs. An install without one saves `Scheduling__TimeZone` (`LOOKOUT_TIME_ZONE` in Docker, default UTC), or else the host's, at startup; once saved, it takes precedence over the environment (README, "Time zone"). Changing it reschedules daily and cron Runs from now in the new zone, with Jitter and the 3-minute minimum, without catching up; interval Watches keep their next Run, and Paused Watches stay unscheduled. Evidence: [`TimeZoneTests`](../../tests/Backend.IntegrationTests/TimeZoneTests.cs), such as `KeepsASavedTimeZoneThroughRestartsWhateverIsConfigured`, `SchedulesDailyAndCronWatchesInTheNewTimeZoneWithoutARestart` and `AScheduleChangedWhileTheTimeZoneChangesIsScheduledInTheNewTimeZone`; [`SchedulingTests`](../../tests/Backend.IntegrationTests/SchedulingTests.cs): `ReschedulesWatchesForANewlyConfiguredTimeZoneWhenAnInstallFirstSavesOne`; e2e [`time-zone.spec.ts`](../../src/frontend/e2e/time-zone.spec.ts).
